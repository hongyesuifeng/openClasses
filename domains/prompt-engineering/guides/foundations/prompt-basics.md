# 提示工程基础指南

> 提示工程学习的起点，掌握核心概念和基础技巧

## 📚 学习目标

完成本指南后，你将能够：
- 理解提示工程的核心概念和原理
- 掌握基础提示模式（零样本、少样本、角色设定）
- 学会使用结构化框架设计有效提示词
- 了解提示词设计的基本原则

## 🎯 适用场景

- 初次接触提示工程的学习者
- 需要系统化提示词知识的开发者
- 希望提升 AI 交互效率的用户

## 1. 提示工程核心概念

### 1.1 什么是提示工程？

提示工程（Prompt Engineering）是优化与大语言模型（LLM）交互的输入（提示词），以获得更准确、更有用输出的技术和方法论。

**核心公式**：
```
高质量输出 = 清晰指令 + 充分上下文 + 合适示例 + 有效约束
```

### 1.2 为什么需要提示工程？

| LLM 特性 | 挑战 | 应对策略 |
|---------|------|---------|
| 概率生成 | 同一输入可能产生不同输出 | 明确格式要求和约束条件 |
| 上下文敏感 | 输出高度依赖提供的信息 | 提供充足相关背景信息 |
| 知识边界 | 训练数据截止日期限制 | 使用 RAG 补充最新知识 |
| 指令遵循 | 需要清晰指令才能准确执行 | 分解任务，步骤化描述 |

## 2. 基础提示模式

### 2.1 零样本提示 (Zero-Shot Prompting)

**定义**：不提供任何示例，直接要求模型完成任务。

**适用场景**：
- 简单、明确的任务
- 模型已具备相关知识
- 对输出格式要求不高

**示例**：
```
请用 Python 写一个计算斐波那契数列的函数。
```

**优化建议**：
- 添加更多上下文信息
- 明确函数签名和要求
- 指定期望的输出格式

### 2.2 少样本提示 (Few-Shot Prompting)

**定义**：提供几个"输入-输出"示例，让模型理解任务模式。

**适用场景**：
- 需要特定输出格式
- 任务规则难以用文字描述
- 需要引导模型风格

**示例**：
```
任务：将游戏术语转换为通俗解释。

示例1：
输入：AOE (Area of Effect)
输出：范围效果 - 指技能或攻击影响一个区域而不是单一目标

示例2：
输入：DPS (Damage Per Second)  
输出：每秒伤害 - 衡量输出伤害的速度，数值越高输出越强

现在请解释：NPC (Non-Player Character)
```

**最佳实践**：
- 提供 2-3 个高质量示例
- 示例应涵盖不同情况
- 保持示例风格一致性

### 2.3 角色设定 (Role Playing)

**定义**：为模型分配特定角色，引导回答风格和专业角度。

**适用场景**：
- 需要专业领域的深度分析
- 希望特定的输出风格
- 需要从特定角度思考问题

**示例**：
```
你是一位拥有 15 年经验的 Unity 游戏性能优化专家。
请分析以下代码可能存在的性能问题，并提供优化建议：

[代码内容]
```

**常用角色模板**：
- 资深软件架构师 - 架构设计和代码审查
- 游戏策划 - 游戏机制设计
- 技术文档编写者 - 文档生成
- 代码审查专家 - 代码质量分析

## 3. 结构化提示框架

### 3.1 CO-STAR 框架

| 部分 | 说明 | 示例 |
|-----|------|-----|
| **C**ontext (背景) | 任务的背景信息 | "我正在用 Unity 开发一个 2D 平台跳跃游戏" |
| **O**bjective (目标) | 你想让模型做什么 | "设计一个存档系统的数据结构" |
| **S**tyle (风格) | 输出的风格 | "以 C# 代码为主，包含详细注释" |
| **T**one (语气) | 回答的语气 | "专业、技术性的语言" |
| **A**udience (受众) | 谁会看这个输出 | "面向中级游戏开发者" |
| **R**esponse (响应) | 输出的具体格式 | "提供类定义、使用示例和注意事项" |

### 3.2 完整提示词模板

```markdown
# 背景
{描述你的项目/任务背景}

# 任务
{清晰描述你想要完成的任务}

# 要求
1. {具体要求1}
2. {具体要求2}
3. {具体要求3}

# 约束条件
- {约束1}
- {约束2}

# 输出格式
{描述期望的输出格式}

# 示例（如果适用）
{提供1-2个示例}
```

## 4. 输出控制技巧

### 4.1 格式控制

**JSON 输出**：
```
请以 JSON 格式输出分析结果，包含 "score", "issues", "suggestions" 三个字段。
只输出 JSON 内容，不要包含任何解释性文字。
```

**Markdown 输出**：
```
请使用 Markdown 格式输出代码，包含语法高亮和适当的标题层级。
```

### 4.2 长度控制

```
请用不超过 200 字概括以下文章的核心观点：
{文章内容}
```

### 4.3 内容约束

```
请分析以下代码的性能问题。
只关注内存分配和 GC 相关问题，不要涉及其他方面。
```

## 5. 提示词设计原则 (CLEAR)

| 原则 | 说明 | 示例 |
|-----|------|-----|
| **C**oncise (简洁) | 去掉废话，直奔主题 | ✅ "实现快速排序算法" <br> ❌ "我想请你帮我实现一个快速排序算法" |
| **L**ucid (清晰) | 避免歧义，使用明确语言 | ✅ "解析 JSON 字符串为对象" <br> ❌ "处理数据" |
| **E**xplicit (明确) | 明确输入输出格式和约束 | ✅ "输出包含 'code' 和 'message' 字段的 JSON" |
| **A**ctionable (可执行) | 提供具体可操作的指令 | ✅ "按以下步骤实现：1.定义接口 2.实现类..." |
| **R**elevant (相关) | 只提供相关信息 | ✅ 在上下文中避免无关内容 |

## 6. 常见错误和调试

### 6.1 常见错误

1. **上下文不足**：模型缺乏必要背景信息
2. **指令模糊**：任务描述不够清晰
3. **缺少约束**：没有明确输出要求
4. **示例质量差**：示例不准确或不一致

### 6.2 调试技巧

**迭代优化**：
1. 从简单提示开始
2. 测试并分析输出
3. 识别问题所在
4. 添加/修改相关部分
5. 重新测试

**A/B 测试**：
- 同时测试多个提示词版本
- 对比不同版本的效果
- 选择表现最好的版本

## 7. 实践练习

### 练习 1：零样本 → 少样本优化

**任务**：让模型识别游戏引擎

**零样本版本**：
```
以下代码是用哪个游戏引擎开发的？
{代码}
```

**少样本优化版本**：
```
任务：识别代码所属的游戏引擎。

示例1：
输入：public class Player : MonoBehaviour {}
输出：Unity C#

示例2：
输入：UCLASS() class APlayer : public ACharacter {}
输出：Unreal Engine C++

现在请识别：
输入：class Player : Node2D {}
输出：
```

### 练习 2：添加角色设定

**基础版本**：
```
这段代码有什么问题？
{代码}
```

**角色设定版本**：
```
你是一位资深的游戏性能优化专家，专门解决内存和性能问题。
请分析以下代码可能存在的性能瓶颈：
{代码}
```

"为我的游戏设计一个背包系统"

```markdown
# 背景

{背包系统的具体需求}

# 要求
{功能要求、技术要求}

# 输出格式
{代码、数据结构、设计文档}
```
