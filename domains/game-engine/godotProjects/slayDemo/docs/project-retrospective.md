# slayDemo 项目全程复盘

> 记录时间：2026-06-12  
> 项目：《甜心迷宫》— 类《杀戮尖塔》Q 版卡牌 Roguelike，Godot 4.x  
> 线索：从 AI 顺畅驱动逻辑层，到 UI 视觉还原遭遇瓶颈，最终决定切回 Cocos 引擎  
> 本文用途：回顾整个推进过程中做了哪些选择、学到了什么、沉淀了哪些可复用的认知

---

## 一、项目起点与选型逻辑

### 1.1 为什么选这个题目

《杀戮尖塔》式游戏之所以成为这次探索的载体，是因为它在复杂度上有一个罕见的特性：**结构复杂，但边界清晰**。

- 游戏循环是确定的闭环（地图推进→战斗→奖励→下一节点）
- 每个子系统（战斗/存档/商店/地图）职责独立，可以分阶段验证
- 游戏设计本身有成熟参考（STS 原版），AI 能立即理解"战斗状态机""卡牌效果枚举"这类概念
- 美术资产要求远低于动作/平台跳跃游戏，早期可以完全依赖 AI 生成图片

**核心判断：这类游戏在逻辑层几乎是纯粹的"有限状态机 + 数据驱动"，非常适合测试 AI 在游戏逻辑开发上能走多远。**

### 1.2 为什么选 Godot

选 Godot 主要出于两个理由：

1. **MCP 工具的存在**。当时 Gopeak-godot-mcp 已经可以让 AI Agent 通过 MCP 协议直接操作 Godot 编辑器（创建场景、添加节点、调属性），理论上可以极大减少"AI 写代码 → 人手动粘到引擎里"这个摩擦环节
2. **GDScript 对 AI 极度友好**。类 Python 语法，几乎没有学习曲线，AI 生成代码质量稳定

**这两个理由都是真实的。MCP 确实在早期验证阶段起了作用（快速创建骨架场景），GDScript 的生成质量确实很高。**

### 1.3 最早期做的最重要的决定：用 JSON，不用 .tres

这是项目第一天就确立的，记录在 `docs/adr/0001-use-json-as-source-data.md`。

Godot 官方推荐用 `.tres`（Resource 文件）存储游戏数据，编辑器原生支持可视化编辑。但这个项目选择了 JSON，理由是：

> JSON 便于 Agent、脚本和工具生成；易于 diff 和审查；可批量编辑。

这个决定在整个项目期间被证明是正确的。它带来了：
- AI 可以直接添加新卡牌，无需理解 .tres 格式
- DataLoader 做集中校验，数据问题在启动时就能发现
- 从 25 张卡扩展到 65 张，0 代码改动
- 测试直接基于 DataLoader 做数据完整性验证

**可复用认知**：对 AI 友好的数据格式 ≠ 对引擎最优的格式。做 AI 协作项目时，数据格式的选择要以"AI 能不能流畅操作"为首要条件，而不是"引擎是否原生支持"。

## 二、逻辑层阶段：AI 协作的最佳形态

### 2.1 架构确立与分层的价值

五层架构（表现 / 应用服务 / 流程 / 玩法逻辑 / 数据）在项目最初就确立，并在整个过程中严格执行：

```
表现层     Scene UI（scenes/）         ← 只订阅信号，不持有业务状态
应用服务层  UIManager / AudioManager   ← 跨场景的服务
流程层     GameState / RunController   ← 状态持久化 + 场景路由
玩法逻辑层  BattleController 等        ← 纯业务，无副作用的静态函数
数据层     DataLoader + JSON           ← 只读
```

这套分层最重要的规则是：**逻辑层不持有任何 UI 节点引用，通过 Signal 广播事件；Scene 层只监听信号被动响应。**

这个规则的实际收益远超预期。因为 Signal 通信意味着：
- BattleController 可以在 headless 模式下运行（没有窗口、没有 UI 节点），单元测试可以直接跑业务逻辑
- VFX 和音效可以各自独立监听同一个 `combat_event` 信号，互不耦合，后期加进去丝毫不影响已有逻辑
- 同一套战斗逻辑在不同 UI 布局下完全可以复用

**可复用认知**：在游戏开发中，"逻辑与表现分离"是说了千遍的原则，但具体到 AI 协作语境下，它还有另一层含义——分离后的逻辑层是 AI 最擅长的领域（确定性输入输出），而分离后的表现层是 AI 摩擦最多的领域（渲染、像素感知）。清晰的分层等于提前划定了"AI 主权区"和"人工介入区"。

### 2.2 Effect 枚举 + 引擎模式：AI 生成效果代码的关键决策

早期面临一个重要岔路：卡牌效果的实现方式。

**方案 A（放弃）：每张卡一个 GDScript 脚本**
```gdscript
# class_name CardStrike extends CardBase
# func execute(): ...
```

**方案 B（采用）：枚举 + 参数，统一 EffectRunner 解释**
```gdscript
# 卡牌数据（JSON）
{ "id": "strike", "effects": [{"type": "damage", "value": 6}] }

# 引擎统一处理
func _apply_effect(effect, battle): 
    match effect.type:
        "damage": _do_damage(effect.value, ...)
```

选方案 B 的理由：新增效果只改引擎+数据，不新建脚本；AI 生成新卡牌只改 JSON，不需要理解代码结构；集中的 EffectRunner 便于统一加日志和调试。

实际效果：项目从初始 13 种效果类型扩展到覆盖毒、格挡、荆棘、抽牌等多个机制，**每次扩展只改 JSON 和 EffectRunner 里的一个 case 分支**，AI 每次操作都精确且无副作用。

**可复用认知**：这是"数据驱动"在代码层面的体现。让 AI 操作数据（JSON），而不是生成大量相似的继承子类。数据是稳定的接口，继承层次是容易错的实现细节。

### 2.3 TDD 的真实价值（不是"代码质量"）

项目从第一天强制 TDD：任何功能没有测试全量通过就不算完成。最终从 0 断言成长到 872+ 断言，全程 Failures: 0。

但 TDD 在这个项目里最重要的价值不是"代码质量更高"——

**它解决的是 AI 协作中的信任问题。**

AI 每次改动，你无法快速人工验证"改对了还是改了新 bug"。测试提供了一个可被机器验证的交付标准：

```
AI 改完 → 运行测试 → 所有断言通过 = 可信任的交付
```

没有这个机制，AI 的每次修改都会产生"到底改对了吗"的焦虑，必须人工 review 所有改动，协作效率会大幅下降。

**测试不是质量保证，是协作信任的基础设施。**

更深的洞察：当测试覆盖足够高时，AI 可以在一次改动中同时修改多个文件（比如重构 EffectRunner + 更新对应测试），因为验证成本接近零。这是纯人工协作里很难做到的事。

**可复用认知**：在任何 AI 协作项目里，尽早建立可自动化的验证机制，不管是单元测试、集成测试还是截图对比。验证闭环的质量决定了 AI 协作的上限速度。

### 2.4 日志系统的 AI 友好设计（Universal Logger）

项目中期引入了 Universal Logger，输出两种格式：
- 控制台文本（人类可读）
- JSON 文件（AI 可解析）

```gdscript
ULogger.battle("回合开始", {"turn": n, "phase": "player", "hand_size": 5})
```

对应的 JSON 日志：
```json
{ "ts": 1780328, "level": "INFO", "module": "BATTLE", "msg": "回合开始", 
  "data": {"turn": 3, "phase": "player", "hand_size": 5} }
```

这个设计的核心思路是：**日志不只是给人看的，也是给 AI 看的**。当运行时出现 bug，AI 可以直接读 JSON 日志，找到出错的模块、时间点和上下文数据，精准定位问题。

实际效果：AI 分析日志 → 定位问题 → 给出修复，全程不需要人工描述"第几步出错了""当时数据是什么状态"。

**可复用认知**：AI 协作项目里，日志系统的设计哲学应该是"双读者"——既服务于人的实时观察，也服务于 AI 的离线分析。结构化（JSON）+ 模块标签 + 数据字段是核心要素。

## 三、第一个关键问题：UI 布局的 AI 不适配

### 3.1 问题的本质

进入视觉打磨阶段后，遭遇了一个系统性问题：**GDScript 里的 UI 布局代码，AI 无法高效操作。**

具体表现：
- UI 布局硬编码在每个场景的 `_build()` 函数里：`panel.position = Vector2(80, 60)`、`label.size = Vector2(320, 28)`
- 7 个场景各有自己的颜色值（`Color(0.95, 0.55, 0.65)`），修改主题要改 7 个地方
- 如果让 AI 直接改 `.tscn` 文件，会破坏节点引用和信号连接——这是 Godot 的内部格式，不是 AI 的母语

**问题的本质是接口问题**，不是 AI 能力问题。AI 能写出正确的 GDScript，但 GDScript 里的 UI 布局代码缺乏稳定的接口——每个改动都可能影响多个地方，且改动效果要运行后才能验证。

### 3.2 解决方案：UIBuilder + JSON Spec

将 UI 描述从 GDScript 抽离到 JSON：

```json
{
  "type": "Button", "name": "EndTurnButton",
  "layout": { "preset": "bottom_right", "size": [140, 60], "margin": [0, 0, 14, 97] },
  "style": "btn_primary",
  "action": "battle.on_end_turn"
}
```

运行时由 UIBuilder 解析生成节点树。AI 只改 JSON，不碰 GDScript 和 .tscn。

配套的是两个 manifest 文件：
- `manifest.assets.json`：资源 key → 路径（AI 用 key，不猜路径）
- `manifest.styles.json`：style key → 视觉配置（换主题只改 manifest）

这套框架建完后，**改 UI 变成了改 JSON——AI 最擅长的操作**。

### 3.3 这个解决方案揭示的更大规律

这是整个项目里最重要的架构认知，值得单独展开：

> **在 AI 协作项目里，任何你希望 AI 参与的环节，都需要有一个 AI 能直接操作的稳定接口。这个接口不能是引擎内部格式（.tscn、.unity、.fire），而应该是通用数据格式（JSON、YAML）。**

具体来说：
- `.tscn` 是 Godot 的内部格式，节点引用用 path 标记，修改一处可能破坏多处。AI 改它，副作用不可控
- `ui_specs/*.ui.json` 是我们定义的接口，每个字段含义清晰，AI 改它，效果可预测

这个模式不是 Godot 独有的，它在任何引擎里都成立：
- Cocos 的 .fire 场景文件 → 应该用 JSON prefab + 脚本构建
- Unity 的 .prefab 文件 → 应该用 ScriptableObject + JSON 驱动
- 任何 GUI 编辑器生成的二进制/复杂格式文件 → 都不适合 AI 直接修改

**可复用认知**："JSON 是 AI 的母语"——在任何新项目里接入 AI 协作时，第一件事是为 AI 可能需要操作的每个领域建立 JSON 接口层。

### 3.4 UIGallery 开发工具：及时反馈的重要性

UIBuilder 框架之外，还引入了 UIGallery——一个运行在游戏里的 UI 预览工具，可以在 Tab 间切换不同场景的 UI 预览，实时显示 JSON 修改的效果。

这个工具的价值在于将反馈循环从"改代码 → 重启游戏 → 进入对应场景"压缩到"改 JSON → 刷新 Gallery"。

**可复用认知**：在 AI 协作项目中，反馈速度决定迭代质量。任何可以压缩反馈循环的工具都值得投入——哪怕这个工具只在开发期使用，用完就丢。

## 四、第二个关键问题：AI 多模态 UI 流水线

### 4.1 流水线的设计动机

UIBuilder 解决了"AI 怎么改 UI"，但没有解决"AI 怎么知道要改成什么"。

视觉还原的难点在于：人看一眼效果图，大脑自动解析出"按钮在右下角、距边 14px、宽 140px"。AI 要做同样的事，需要一个中间步骤——将图片转化为结构化的坐标和属性描述。

**这就是 visual.json 的来由：它是效果图（图像感知）和 UI Spec（工程实现）之间的中间层。**

### 4.2 完整流水线设计

```
ChatGPT 生成 target.png（效果图 + 美术资源）
     ↓
视觉拆解 → ui_design_specs/<scene>.visual.json
  每个元素标注：bbox 坐标、节点类型、锚点方式、style_key、asset_key、容差值
     ↓
资源清单 → manifest.assets.patch.json + manifest.styles.patch.json
     ↓
Coding Agent 合并 patch + 修改 ui_specs/<scene>.ui.json
     ↓
Godot headless 渲染 → ui_snapshots/current/<scene>_current.png
     ↓
视觉模型对比 target vs current → delta.json（偏差量化）
     ↓
Coding Agent 按 delta 微调 → 下一轮
```

注意这条流水线里每个环节的工具选择是刻意的：
- 效果图生成：ChatGPT（图像生成能力）
- 视觉拆解：ChatGPT / Claude（多模态理解）
- 工程实现：Claude Code（代码执行）
- 渲染截图：Godot headless（引擎原生，精确）
- 视觉对比：视觉模型（图像感知）

**这不是"最强 AI 一把梭"的思路，而是"每个环节用最适合的工具"。**

### 4.3 visual.json 的设计细节：容差（tolerance）字段

这是流水线里最细致的设计之一，值得单独讲：

```json
{
  "id": "end_turn_btn",
  "bbox": [1135, 570, 131, 53],
  "tolerance": {
    "position_px": 6,
    "size_px": 6,
    "color_delta": 8
  },
  "acceptance_weight": 0.95
}
```

每个元素都有容差参数——结束回合按钮（核心交互）容差 ±6px，装饰元素容差 ±20px，背景图容差 ±30px。

这个设计解决了一个实际问题：视觉对比模型告诉你"有差异"，但它无法判断这个差异是否值得修复。容差字段将这个判断提前编码进了规格里，让 AI 可以自动过滤不重要的差异，集中精力处理高权重元素。

**可复用认知**：在任何需要"量化比对"的场景（UI、性能指标、数值平衡），不要只定义"目标值"，还要定义"可接受范围"。没有容差的精确目标会产生永无止境的微调，有容差的目标会产生清晰的完成标准。

### 4.4 流水线真正落地的情况

从 commit 记录来看，这条流水线在主菜单、地图、战斗场景上都跑通了。但"跑通"和"顺畅"之间有很大的距离。

每接入一个新场景，都要经历类似的问题：
- 背景图带有 UI 残影（合成图，不是干净底图）
- 占位图标没有被替换（manifest key 存在，但对应的 PNG 是个方框）
- 动态区域在预览状态下没有 mock 数据，截图是空白
- 某个节点在 target.png 里有，但 visual.json 里没有标注

这些问题的共同特征：**不是代码逻辑问题，是资源语义问题**。Lint 工具能检查 key 是否存在，但无法检查"这张 PNG 的内容是否真的是按钮图"——这件事只有人眼才能判断。

## 五、瓶颈的真实形态

### 5.1 "可测试"与"可感知"的分界线

回顾整个项目，有一条非常清晰的分界线：

**可测试的部分（AI 效率极高）：**
- 战斗状态机的状态转移：输入确定 → 输出确定 → 可以写断言
- DataLoader 的数据校验：JSON 字段格式 → 可以枚举所有合法值
- 存档系统的序列化/反序列化：写入 → 读回 → 比对
- 地图生成的连通性：生成的 DAG 是否每层有路径

**不可测试、只能感知的部分（AI 效率下降）：**
- 背景图是否"干净"（不含 UI 残影）
- 按钮图标是否"视觉上正确"（不是占位方框）
- 整体风格是否"看起来像马卡龙主题"
- 动画帧率是否"流畅"

后者有一个共同点：**判断标准存在于人的感知里，无法被数字化成可自动验证的条件。**

**这不是 AI 的缺陷，而是这类问题的本质**——它们需要视觉感知，而视觉感知目前仍需要人参与验证环节。

### 5.2 Godot 引擎知识缺口的累积效应

除了感知问题，还有一类摩擦是纯粹的"引擎知识缺口"：

**Layout Preset 映射**：Godot 有 15 种 Layout Preset，每种对应不同的锚点和边距计算规则。UIBuilder 需要把这 15 种 preset 正确映射到 Godot 的 anchor 数值。AI 在写这部分代码时会产生微妙偏差，而偏差只在渲染后才能发现。

**节点生命周期时序**：`add_child` 后节点不立即生效，需要 `call_deferred`；SubViewport 需要下一帧才能正确渲染。这类时序 bug 产生了多次"预览截图空白"或"尺寸设置无效"的现象（commit `91376477`、`414a7ac6` 都是修复这类问题）。

**headless 测试环境**：Godot headless 模式下，插件加载顺序与编辑器启动不同，`class_name` 全局引用会失效。UIBuilder 框架专门为此做了适配——内部全部用 `preload()` 而不是 `class_name`。

每一类摩擦单独看都不是大问题，但累积起来，修复每个小问题都需要有经验的人介入指引，或者 AI 反复试错。

**关键认知**：陌生引擎里的"领域知识"（API 时序、内部机制、格式约定）是 AI 协作效率的隐性成本。这个成本在逻辑层可以被 TDD 缓冲（跑一遍测试就知道对不对），但在表现层没有自动缓冲机制，只能靠人工经验或反复试错。

### 5.3 工具建设的两种动力

回看整个项目的工具建设：UIBuilder 框架、Gallery 预览工具、visual.json 中间层、ui_lint.gd、render_ui_preview.gd……

这些工具本身质量都很高，很多是通用的。但它们的建设动力可以分成两类：

**第一类：解决真正的通用问题**
- JSON 驱动 UI（任何引擎都可以用这个思路）
- visual.json 中间层（任何需要视觉还原的场景都需要这个）
- 测试自动化（所有项目都需要）
- 结构化日志（所有 AI 协作项目都需要）

**第二类：弥补陌生引擎的知识缺口**
- UIBuilder 里对 15 种 Layout Preset 的映射（Godot 特有）
- headless 模式下 class_name 引用的替代方案（Godot 特有）
- Gallery 里对 SubViewport 时序问题的处理（Godot 特有）
- cmd.exe 包装 Godot 二进制文件的 WSL 适配（Godot + WSL 特有）

第一类工具是资产，切换到 Cocos 后仍然有用。第二类工具是成本，切换到 Cocos 后归零，而且在 Cocos 里会产生新的类似成本。

**当第二类工具的建设成本持续超过第一类工具的价值积累时，就是考虑切换引擎的时机。**

## 六、切引擎的决策逻辑

### 6.1 切引擎不是"放弃"

这是最容易被误解的地方。切回 Cocos 不等于"Godot 失败了"或者"这段时间白费了"。

正确的理解是：**这个项目的目标是验证 AI 协作游戏开发的方法论，而不是在 Godot 上完成一个游戏。** 目标已经完成：

- 验证了 AI 在逻辑层的效率上限（非常高）
- 验证了 AI 协作的核心工作方式（TDD + JSON 接口 + 结构化日志）
- 识别了 AI 在表现层的瓶颈（感知问题无法自动化）
- 建立了 AI-引擎接口层的设计模式（JSON 驱动 + visual 中间层）

现在切回 Cocos，是把这套已验证的方法论迁移到一个摩擦更低的环境里继续推进，而不是从头开始。

### 6.2 决策的判断依据

切引擎时做了一个简单的评估：

| 问题 | 答案 |
|------|------|
| Cocos 里是否有对应 Godot 陌生知识成本的问题？ | 有，但成本极低（TypeScript + 熟悉的 Web 渲染管线）|
| 已验证的架构（五层分层、数据驱动等）能否在 Cocos 里复用？ | 完全可以，与引擎无关 |
| JSON 驱动 UI 的模式在 Cocos 里是否成立？ | 更自然（Cocos 本身更接近 Web 生态）|
| AI 协作模式（TDD、日志、visual.json 中间层）是否需要重建？ | 不需要，方法论是通用的 |

**结论：收益 >> 成本，果断切换。**

## 七、沉淀：具体可带走的东西

### 7.1 架构设计模式（代码级）

**五层架构**，可直接平移到任何引擎：
- 数据层：JSON 驱动，DataLoader 集中校验
- 玩法逻辑层：纯函数（静态方法），无副作用，无 UI 引用
- 流程层：GameState 全局单例，RunController 驱动场景路由
- 应用服务层：AudioManager、UIManager，封装跨场景能力
- 表现层：只监听事件，不持有业务状态

**卡牌效果引擎模式**（数据驱动 + 统一引擎）：
- 不用继承，用枚举+参数描述效果
- 统一的 EffectRunner 解释执行
- 扩展只加数据和 case 分支，不新增脚本
- 这个模式在任何"需要大量同类但有差异的对象"的系统里都适用（技能系统、buff 系统、道具系统）

**存档系统设计**：
- 序列化：GameState 全量导出为 Dictionary → JSON
- 恢复：反序列化 + 重建运行时对象（注意 instance_id 续接）
- 自动存档时机：节点完成时（不是定时器），保证存档点与游戏状态严格对齐

### 7.2 AI 协作方法论（流程级）

**JSON 作为 AI-引擎接口层**

核心规则：任何你希望 AI 操作的游戏领域，都要有 JSON 接口。具体应用：
- 卡牌/敌人/遗物数据 → JSON
- UI 布局 → JSON Spec（ui_specs）
- 资源映射 → JSON manifest
- 样式配置 → JSON manifest

**visual.json 中间层（效果图 → 工程实现）**

当你有 UI 效果图，需要 AI 还原成代码时，不要直接"让 AI 看图写代码"。正确流程：
1. AI 看图 → 输出 visual.json（结构化拆解：每个元素的坐标、类型、绑定）
2. AI 读 visual.json → 修改 Spec JSON
3. 渲染截图 → 与 target 对比 → 量化差异（含容差）→ 精确修复

**manifest patch 机制（增量变更）**

不要让 AI 直接修改全局 manifest，而是生成 patch 文件，由 Coding Agent 合并。避免多轮修改的覆盖冲突，也让每次变更有明确的 scope。

**Agent 权限边界声明**

在项目的 CLAUDE.md / AGENTS.md 里明确声明：
- 允许修改哪些文件（UI spec、manifest、ui_components）
- 禁止修改哪些文件（战斗逻辑、autoload、主场景 .tscn、游戏数据 JSON）

这不是"限制 AI"，而是**让 AI 的操作有明确边界，减少不可预期的副作用**。

### 7.3 验证体系设计（基础设施级）

**三层验证体系**：

| 层级 | 验证对象 | 工具 | 自动化程度 |
|------|---------|------|-----------|
| 逻辑层 | 业务规则、数据完整性 | 单元测试 + 集成测试 | 完全自动化 |
| 结构层 | JSON 格式合法性、key 引用 | Lint 脚本 | 完全自动化 |
| 视觉层 | 像素还原程度 | 截图 + 人工对比 | 半自动化 |

前两层都是 AI 可以独立完成闭环的——改完自己跑验证，不需要人参与。第三层需要人介入，这是上限，目前无法突破。

**关键认知**：把大量精力投入到前两层的验证体系建设上，让 AI 能自我验证的范围尽可能大。第三层控制在最小必要范围（只验证 acceptance_weight 高的核心元素）。

**结构化日志（双读者设计）**：
- 关键业务节点必须有日志
- 日志包含足够的上下文数据（不只是消息字符串）
- JSON 格式，AI 可以直接 grep 分析
- 模块标签（BATTLE / UI / AI / LIFECYCLE），便于按领域过滤

### 7.4 项目管理经验（过程级）

**多角色 Agent 系统的价值**

制作人/开发者/美术/策划四个视角，不只是学习工具，它们是**系统性盲点检测机制**。

典型案例：V1.0 时，开发者视角发现代码质量问题（seed 非确定性、遗物效果类型单一），但制作人视角发现的是"遗物图标覆盖率只有 31%"和"商店误操作风险"——这两个问题从开发者视角根本不会被优先注意到，但它们是阻断玩家体验的关键因素。

**文档随代码演进**

每次里程碑结束都生成一份项目状态快照（按日期命名），记录当前进度、测试数、已知问题和决策依据。这让"过去的状态"随时可以查阅，而不是只能从代码推断。

**复盘要追根因，不能只记现象**

`docs/tech/17-ui-restoration-lessons.md` 是这个项目里设计得最好的文档之一。每次 UI 还原问题修复后，必须追加一条记录，格式是：症状 → 根因 → 修复动作 → 沉淀规则 → 验证结果。

这个规则的本质是：**错误本身不是最有价值的，错误背后的规律才是**。如果只记"背景图发糊，改了一下好了"，下次遇到同类问题还是从零开始。如果记"根因是 backgrounds.map_event 是带 UI 残影的合成图，规则是背景资源必须先视觉验证无 UI 烘焙"，下次可以在生成阶段就拦截这类问题。

## 九、一句话版本（核心认知提炼）

1. **AI 擅长逻辑，不擅长感知**——战斗系统、存档、数据验证可以完全 AI 主导；视觉还原需要人介入。清晰分层等于提前划定 AI 主权区。

2. **JSON 是 AI 的母语**——任何你希望 AI 参与的领域，先建 JSON 接口层，再让 AI 操作这个接口。引擎内部格式（.tscn、.fire、.prefab）不适合 AI 直接修改。

3. **测试不是质量保证，是协作信任的基础设施**——没有自动化验证，AI 的每次改动都需要人工 review，协作上限很低。

4. **日志要面向两个读者**——人（实时观察）和 AI（离线分析）。结构化 JSON + 模块标签 + 数据字段是核心。

5. **容差比目标更重要**——在任何量化对比场景里（UI 还原、性能指标），定义"可接受范围"比定义"精确目标"更有价值。没有容差的精确目标会产生无休止的微调。

6. **切换成本 < 摩擦积累成本时，就应该切换**——陌生引擎的知识缺口是持续性隐性成本。当弥补这个缺口的工具建设超过了功能开发本身，切换到熟悉环境是正确决定。
