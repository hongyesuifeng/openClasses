# 00 - 执行原则

## 目标

把一个学习型 Demo 做成“可玩、可验证、可持续推进”的项目，而不是把时间消耗在无限扩张的功能清单里。

这一篇的作用，是在真正开工前先给整个项目设边界。边界对了，后面每一篇执行文档才有意义；边界错了，后面做得越多，返工越大。

## 这一版 Demo 的定位

这一版 Demo 不是：

- 完整复刻《杀戮尖塔》；
- 商业可售卖成品；
- 一次性沉淀出完整通用框架；
- 证明你已经彻底掌握 Godot 的全部模块。

这一版 Demo 是：

- 一个可完整打通的最小卡牌 Roguelike 原型；
- 一个让你把 Godot 基础使用、技术原理、AI 辅助开发串起来的实战项目；
- 一个让你在真实问题里反推源码与架构理解的学习抓手。

## 核心原则

### 1. 先闭环，再扩展

先完成：

`抽牌 → 出牌 → 结算 → 敌人行动 → 下一回合 → 战斗结束`

只有这个闭环跑通了，后面的地图、奖励、事件、遗物、升级才有意义。

### 2. 先可用，再优雅

先让系统明确分工并跑起来，再逐步优化命名、拆分结构、沉淀模块。学习型项目最常见的问题不是代码不够优雅，而是“还没能玩就先想搭框架”。

### 3. AI 只负责加速，不负责代替判断

AI 适合做：

- 生成脚手架；
- 帮你列测试清单；
- 帮你补资源样板；
- 帮你把需求变成任务列表。

AI 不适合替你做：

- 项目边界判断；
- 核心系统职责划分；
- 是否应该抽象为复用模块的决策。

### 4. 一切以运行结果为准

任何设计、命名、结构、抽象，都必须回到 Godot 项目中验证。只要它不能实际支撑项目推进，它就不是当前优先级最高的工作。

### 5. 以问题驱动理解源码

源码阅读不应该脱离项目进行。你在 Demo 中遇到“为什么这里要这样组织场景”“为什么资源这样加载”“为什么 UI 这样串信号”的问题时，再回看源码，理解会更扎实。

## 范围控制

### 首版强制保留

- 1 个角色
- 20~30 张卡牌
- 6~8 个敌人
- 1 个 Act 或 1 段最小地图推进
- 1 套基础奖励流程
- 仅桌面平台导出

### 首版强制不做

- 多角色、多章节
- 复杂剧情系统
- 大量特殊遗物与事件分支
- 在线功能
- 完整 meta progression
- 过早抽象成通用框架

## 你每天的判断标准

如果你当天新增的工作不能帮助下面任一项成立，就先不要做：

1. 更快让最小可玩闭环跑通；
2. 更清楚地分离数据、逻辑、表现；
3. 更稳定地让当前 Demo 被测试与试玩；
4. 更明确地暴露值得回看源码的问题。

## 完成标准

### 项目完成标准

- 能从头跑完一局；
- 玩家能看懂基础交互；
- 主要系统边界清楚；
- 能导出桌面版并给别人试玩；
- 有一份明确的后续复用模块候选清单。

### 阶段完成标准

每推进一个阶段，都至少要满足：

- 有可运行的结果，不是只有笔记；
- 有一个阶段性验收结论；
- 有一个清晰的下一步动作；
- 有一个你目前真正不理解、值得后续回看原理/源码的问题。

## 常见坑

1. **把所有系统同时推进**：战斗、地图、UI、奖励一起做，结果全部都半成品。
2. **过早做抽象**：在还没有稳定需求前，先写事件总线、状态机框架、UI 管理器，最后发现全要重写。
3. **只做功能，不做验收**：以为“差不多写完了”，但没有实际玩过完整一局。
4. **用 AI 生大量代码但不验证**：生成得快，返工更快。
