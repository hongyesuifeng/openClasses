# 03 - 战斗与资源数据

## 目标

把战斗系统从“现在能跑”整理成“后面还能继续加内容而不会迅速失控”的结构。这个阶段的重点不是增加更多玩法，而是让数据、逻辑、表现各自回到正确位置。

## 前置

进入这一阶段前，你至少已经：

- 做出了最小可玩闭环；
- 确认玩家和敌人的战斗流程已经能跑通；
- 确认目前最痛的点是什么：数据难扩、状态难管、效果难加，还是敌人逻辑太写死。

## 结构目标

这一阶段结束后，你应该开始形成下面的分层意识：

- **数据层**：定义卡牌、敌人、状态、奖励是什么；
- **逻辑层**：决定这些数据在战斗里怎么生效；
- **表现层**：负责展示、动画、反馈；
- **流程层**：决定什么时候轮到谁做什么。

## 数据层建议

### 建议最先资源化的对象

- `CardData`
- `EnemyData`
- `StatusData`
- `RewardData`
- 可选 `EncounterData`

### 为什么先做资源化

因为卡牌类游戏最容易失控的地方，是新内容越来越多时，所有规则都写死在脚本里。只要你把“定义”和“执行”拆开，后面扩内容的成本会低很多。

### 最少应包含的信息

#### CardData

- 名称
- 费用
- 描述
- 稀有度
- 目标类型
- 效果列表

#### EnemyData

- 名称
- 生命值
- 意图池或动作序列
- 基础数值

#### StatusData

- 名称
- 图标/描述
- 触发时机
- 叠层规则
- 持续方式

## 逻辑层建议

### 1. 卡牌效果结算

卡牌逻辑尽量不要直接写在 UI 脚本里。更合理的方式是：

- UI 负责发出“使用了哪张牌”的动作；
- 战斗逻辑层负责解释这张牌要产生什么效果；
- 表现层负责把结果播出来。

### 2. 敌人意图与行动

敌人逻辑建议分成两段：

- **意图生成**：下一回合准备做什么；
- **行动执行**：真正把伤害、格挡、状态等打到目标身上。

这样做的好处是，UI 可以显示意图，逻辑也更容易测试。

### 3. 状态效果管理

状态系统一开始就要明确：

- 什么时候触发；
- 如何叠层；
- 何时减少层数或移除；
- 多个状态的结算顺序是什么。

如果这些规则不先确定，后面一旦加中毒、易伤、虚弱之类效果，就会非常乱。

### 4. 奖励发放

奖励系统不用一开始就复杂，但至少要把“战斗胜利”和“战后获得什么”拆开，不要把战斗脚本直接写成一坨结算兼奖励兼跳场景逻辑。

## 结构要求

- 数据和表现分离；
- 回合与 UI 分离；
- 卡牌逻辑尽量 Resource 化；
- 不把规则写死在单个场景脚本里；
- 一类问题尽量只在一层解决。

## 阶段产出

- 一套可继续扩内容的数据资源结构；
- 一套不会和 UI 强耦合的战斗逻辑；
- 一个更清楚的状态/效果结算方式；
- 一个基本可维护的敌人行为模型。

## 验收

- 新增一张卡牌时，不需要复制大量逻辑代码；
- 新增一个敌人时，不需要重写整个战斗流程；
- 状态效果的触发时机可以被明确解释；
- UI 脚本不负责决定核心规则。

## 常见坑

1. **一切都塞进 BattleManager**：短期快，长期最痛。
2. **Resource 只当静态配置，不承担结构价值**：导致数据和逻辑仍然混在一起。
3. **敌人逻辑全写在场景节点里**：后面几乎无法复用。
4. **状态效果没有统一触发时机**：问题一多就只能靠 if-else 堆。
