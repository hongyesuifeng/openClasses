# 01 - 项目启动

## 目标

先把工程骨架搭稳，保证后续所有功能都有明确落点。项目启动阶段做得越清楚，后面越不容易在“脚本放哪、资源放哪、状态放哪、入口在哪”上反复返工。

## 前置

开始前你至少需要：

- 已安装 Godot 4.x stable；
- 看过总览文档里的范围控制；
- 明确这一版只做桌面版；
- 明确首版 Demo 的最小玩法范围。

## 目录建议

推荐先用下面这套结构，不要求一次到位，但至少骨架要先建立：

```text
slay_demo/
├── scenes/
│   ├── app/
│   ├── battle/
│   ├── map/
│   ├── reward/
│   └── ui/
├── scripts/
│   ├── autoload/
│   ├── battle/
│   ├── cards/
│   ├── enemies/
│   ├── map/
│   ├── systems/
│   └── ui/
├── resources/
│   ├── cards/
│   ├── enemies/
│   ├── statuses/
│   └── encounters/
├── autoload/
├── assets/
└── tests/
```

## 执行步骤

### 第 1 步：创建空项目并固定版本

1. 使用 Godot 4.x stable 创建项目；
2. 项目名先简单直接，例如 `slay_demo`；
3. 不要一开始启用太多插件；
4. 先确保空项目能正常启动。

### 第 2 步：建立目录与命名规则

你现在就要确定：

- 场景文件统一放在 `scenes/`
- 逻辑脚本统一放在 `scripts/`
- 数据资源统一放在 `resources/`
- 全局脚本只放少量在 `autoload/`

命名建议：

- 场景：`BattleScene.tscn` / `MainMenu.tscn`
- 脚本：`battle_manager.gd` / `card_data.gd`
- 资源：`strike_card.tres` / `slime_enemy.tres`

### 第 3 步：先建立少量自动加载

这一阶段不要把所有“未来可能需要的系统”都做成 autoload。只保留当前确实需要的：

- `GameState`：记录当前整体流程状态；
- `SceneRouter` 或等价能力：统一场景切换；
- 可选 `EventBus`：如果你已经明确存在跨界面、跨系统广播需求。

不建议现在就上：

- 复杂 SaveManager
- 全能型 ServiceLocator
- 大而全的全局管理器

### 第 4 步：建立最小场景集合

至少准备这几个场景：

- `AppRoot`：应用入口
- `MainMenu`：开始入口
- `BattleScene`：战斗主场景
- 可选 `RewardScene`：战斗后奖励占位

这里的关键不是内容丰富，而是路径稳定、切换稳定。

### 第 5 步：写一份结构说明

在真正进入战斗逻辑前，你要能用自然语言说明：

- 哪些是数据文件；
- 哪些是表现层场景；
- 哪些是流程推进脚本；
- 哪些脚本不应该互相直接引用。

如果你自己都讲不清，这个结构通常还不够稳定。

## 产出

- 一个可打开、可运行的 Godot 项目；
- 一套清晰的项目目录结构；
- 一个稳定的入口场景；
- 少量但职责明确的 autoload；
- 至少一个可切换到战斗场景的主流程。

## 验收

- 项目能运行；
- 主菜单能进入战斗场景；
- 目录结构不混乱；
- 全局状态没有散落在多个看不懂的单例里；
- 你能解释每一个顶层目录为什么存在。

## 常见坑

1. **先做系统，再建目录**：最后逻辑和资源乱塞。
2. **autoload 太多**：什么都做成全局，后面边界会越来越糊。
3. **入口场景不稳定**：导致后面每次调试都靠手工切场景。
4. **命名不统一**：越做越难找文件。
