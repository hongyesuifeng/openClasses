# 02 - 最小可玩闭环

## 目标

先做出一个真正“能玩起来”的闭环，而不是做一堆彼此没有打通的子系统。只要这个阶段完成，你就已经拥有了一个最小游戏，而不是一堆零件。

## 前置

开始前应当已经具备：

- 稳定的项目结构；
- 能正常进入战斗场景；
- 基础 autoload 已就位；
- 你已经接受这阶段只做最小玩法，不补复杂内容。

## 核心循环

最小闭环必须完整包含：

1. 开始战斗；
2. 初始化玩家与敌人；
3. 抽起始手牌；
4. 玩家出牌；
5. 进行数值结算；
6. 敌人行动；
7. 进入下一回合；
8. 进行胜负判定。

只要这 8 步任何一步还没有真正跑通，就不要急着做地图、奖励、商店、事件。

## 执行步骤

### 第 1 步：先打通回合状态

至少明确这些状态：

- `battle_start`
- `player_turn`
- `player_resolve`
- `enemy_turn`
- `battle_end`

你不一定非要马上写成正式状态机，但你必须能清楚表达“当前系统正处于哪一步”。

### 第 2 步：实现卡组的最小流转

先做：

- 抽牌堆
- 手牌
- 弃牌堆

再做：

- 抽牌
- 打牌
- 弃牌
- 牌堆为空时洗牌回抽牌堆

这一步的关键不是动画，而是数据流转正确。

### 第 3 步：实现最小能量系统

至少保证：

- 玩家回合开始时重置能量；
- 打牌时检查能量是否足够；
- 打出卡牌后能量正确扣减；
- 回合结束时状态能正确收束。

### 第 4 步：实现最小卡牌效果

先只做最基本效果即可：

- 造成伤害
- 获得格挡
- 抽牌

不要一开始就做复杂条件、嵌套触发、多层状态联动。

### 第 5 步：实现最小敌人行为

敌人逻辑先保持简单：

- 固定动作序列；
- 或简单权重池；
- UI 上能看到敌人意图；
- 敌人回合能完成一次实际行动。

### 第 6 步：补上胜负判定

你需要确保：

- 玩家生命归零会进入失败；
- 敌人全部死亡会进入胜利；
- 战斗结束后不会继续推进回合。

## 阶段产出

- 一个能完整走完回合的战斗原型；
- 一个能真实输赢的最小玩法；
- 一组已经被验证过的基础战斗脚本；
- 一套之后能继续扩展的回合推进骨架。

## 验收

- 进入战斗后能自动开始第一回合；
- 玩家可以抽牌、出牌、结束回合；
- 敌人能执行最小行动；
- 伤害、格挡、抽牌这些基础效果能正确结算；
- 可以明确地输掉或赢下一场战斗。

## 常见坑

1. **先做复杂效果系统**：结果最基本的出牌都还没跑通。
2. **把 UI 和逻辑绑死**：一改表现就影响战斗推进。
3. **没有显式回合状态**：问题一多就不知道卡在哪个阶段。
4. **战斗能开始但不能结束**：这是非常典型的“看起来能玩，实际没闭环”。
