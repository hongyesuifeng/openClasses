# 05 - 调试、测试与发布

## 目标

把 Demo 从“开发者自己觉得差不多了”推进到“真的可以交给别人试玩”。这一阶段的重点不是再加功能，而是把已有内容变稳定、可验证、可交付。

## 前置

开始前应至少已经具备：

- 一套完整可玩的最小循环；
- 清楚的 UI 与交互流；
- 基本稳定的数据与战斗结构；
- 一份你知道当前有哪些已知问题的清单。

## 验证维度

### 1. 功能正确性

重点检查：

- 回合切换是否稳定；
- 抽牌 / 弃牌 / 洗牌是否正确；
- 卡牌费用和效果是否一致；
- 敌人意图和实际行为是否一致；
- 战斗结束后流程是否正确收束。

### 2. 可玩性

重点检查：

- 玩家是否知道现在该做什么；
- 新玩家是否能在短时间内理解基础玩法；
- 是否存在明显卡关但不是策略问题，而是信息表达问题。

### 3. 稳定性

重点检查：

- 是否存在软锁；
- 是否存在动画和逻辑不同步；
- 是否存在异常输入打乱状态的问题；
- 是否存在多次切场景后状态残留。

### 4. 交付性

重点检查：

- 导出流程是否稳定；
- 桌面版是否能直接运行；
- 试玩说明是否足够清楚；
- 页面或说明文档是否真实反映当前完成度。

## 执行步骤

### 第 1 步：先做功能测试清单

不要凭感觉测。至少列出：

- 开局流程
- 抽牌和手牌上限
- 能量恢复与扣减
- 敌人回合
- 胜利 / 失败流程
- 奖励流程
- 场景切换

### 第 2 步：跑完整试玩流程

你自己至少要完整打若干局，并记录：

- 出现了什么 bug；
- 哪些信息表达不清楚；
- 哪些地方节奏很拖；
- 哪些问题是功能错误，哪些是体验问题。

### 第 3 步：让别人试玩

如果条件允许，找至少一个不是你自己的人试玩。你主要看的是：

- 他是否知道怎么开始；
- 他是否知道什么时候该结束回合；
- 他是否能看懂敌人意图；
- 他卡住时是因为策略，还是因为你的设计没表达清楚。

### 第 4 步：整理已知问题并分优先级

把问题至少分成三类：

- 阻塞交付：必须修；
- 明显影响体验：建议修；
- 可留到下一版：暂不修。

### 第 5 步：准备导出与试玩材料

至少要准备：

- 桌面版导出包；
- 一页最简说明；
- 已知问题说明；
- 更新日志或版本号。

## 阶段产出

- 一份可执行的测试清单；
- 一版已整理过问题优先级的 Demo；
- 一个可导出的桌面版；
- 一份别人能看懂的试玩说明。

## 验收

- 能从头打完一局；
- 没有阻塞推进的 bug；
- 别人能打开并试玩；
- 当前版本的问题是“已知且可解释”的，而不是“随机冒出来的”。

## 常见坑

1. **一直加功能，不做交付检查**：最后什么都有一点，但没有一版可试玩。
2. **只自己试玩**：很多表达问题自己已经习惯，看不出来。
3. **不记录问题**：每次测出同样的问题，却没有形成修复顺序。
4. **导出太晚才做**：临近结束才发现资源路径、平台设置一堆问题。
