# 06 - 可复用模块沉淀

## 目标

把这次 Demo 中已经被真实验证过、反复出现、明显值得复用的能力，整理成下一次可以直接使用的模块。重点不是“为了优雅而抽象”，而是把已经证明有价值的结构沉淀下来。

## 前置

这一篇默认你已经：

- 完成了当前 Demo 的主闭环；
- 跑过测试和试玩；
- 知道哪些结构反复出现、哪些地方最容易重复劳动；
- 能区分“这次临时写法”和“下次仍然会需要的能力”。

## 为什么放到最后做

因为只有当你已经真的做完一个项目，你才知道：

- 哪些能力确实反复出现；
- 哪些抽象在真实项目里站得住；
- 哪些模块只是你一开始想象中“看起来应该很通用”，实际并不稳定。

如果太早做复用层，最容易得到的是“一个很漂亮但不适合当前项目、也未必适合下一个项目的框架”。

## 优先沉淀方向

### 1. 事件系统

适合在这些情况沉淀：

- 多个系统都需要知道“发生了一件事”；
- UI、战斗、奖励之间存在广播式通信；
- 你已经反复在写同类信号中转逻辑。

沉淀时重点关注：

- 事件命名是否稳定；
- 事件边界是否清楚；
- 哪些事件应全局广播，哪些只在局部使用。

### 2. UI 管理系统

适合在这些情况沉淀：

- 你已经有多层界面切换；
- 弹窗、提示、结算界面有统一行为；
- 输入屏蔽和层级管理逻辑开始重复。

沉淀时重点关注：

- 打开/关闭界面的生命周期；
- 层级与输入焦点规则；
- 通用界面和业务界面的边界。

### 3. 状态机

适合在这些情况沉淀：

- 回合、角色行为、流程推进已经有明确状态；
- if-else 逐渐过多，流程切换越来越难维护；
- 多个系统都需要共享“当前阶段”的概念。

沉淀时重点关注：

- 状态定义是否真的稳定；
- 状态进入/退出时是否有统一约束；
- 状态机是全局流程级的，还是局部对象级的。

### 4. 资源管理模块

适合在这些情况沉淀：

- 资源加载路径越来越多；
- 缓存、预加载、动态加载规则开始重复；
- 不同数据资源已经有共同约束。

沉淀时重点关注：

- 资源加载入口是否统一；
- 缓存策略是否明确；
- 编辑器资源与运行时资源是否区分清楚。

## 沉淀方法

建议按这个顺序做：

1. 回顾当前 Demo 中重复出现的写法；
2. 标出哪些重复是稳定模式，哪些只是临时权宜；
3. 只抽象最稳定、最常用、最容易复用的那部分；
4. 在下一个 Demo 中验证，而不是立刻重构当前项目全部代码。

## 不建议现在做的事

- 把当前 Demo 整体重构成“通用框架”；
- 一次性把所有系统都抽成库；
- 为了复用而牺牲当前项目的可读性；
- 在没有第二个项目验证前就过度设计接口。

## 阶段产出

- 一份明确的复用模块候选清单；
- 一套经过当前项目验证的通用模式；
- 一批可以在下一次 Demo 中直接尝试的基础能力。

## 验收

- 你能说清每个模块为什么值得复用；
- 你能指出它在当前 Demo 里解决了什么重复问题；
- 你不会为了沉淀复用模块而打断当前 Demo 的完成状态。

## 最终结论

这一步的本质，不是“把项目做得更高级”，而是把一次真实完成的项目经验，转化为下一次能直接提高效率的工程资产。
