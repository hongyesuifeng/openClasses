# Demo 执行落地

本章节负责把 `godot-comprehensive.md` 里的主线规划，落实成一套可直接执行的项目推进文档。它不再讨论“学什么”，而是回答“今天该做什么、做到什么算完成、卡住时先检查什么”。

目标只有一个：**做出一个范围受控、可完整交付、能支撑后续源码理解的类《杀戮尖塔》Demo**。

## 你会得到什么

这套文档会把执行路径拆成 7 个阶段，每个阶段都包含：

- 目标：这一阶段要解决什么问题；
- 前置：开始前必须具备什么；
- 操作步骤：建议按什么顺序推进；
- 产出：这一阶段结束后应该看见什么；
- 验收：什么条件满足了才算真正完成；
- 常见坑：最容易浪费时间的点；
- 下一步：应该无缝进入哪个阶段。

## 推荐推进顺序

### 第 1 段：先把项目跑起来

依次完成：

1. `00-执行原则`
2. `01-项目启动`

这一步结束时，不要求你已经“会做游戏”，但你必须已经有：项目结构、入口场景、基础自动加载、清晰的命名规则。

### 第 2 段：先做出可玩的骨架

依次完成：

1. `02-最小可玩闭环`
2. `03-战斗与资源数据`

这一步结束时，应该至少能打完一场最小战斗。它可以丑，可以简陋，但不能是“只做了一堆零件”。

### 第 3 段：把玩家体验补完整

依次完成：

1. `04-UI 与交互流`
2. `05-调试测试与发布`

这一步结束时，Demo 应该能给别人试玩，而不是只适合自己调试。

### 第 4 段：完成后再沉淀复用能力

最后再做：

1. `06-可复用模块沉淀`

这一段不属于当前 Demo 的前置工程，而是把已经被验证过的模式，沉淀成下一个项目的复用基础。

## 每周建议节奏

- 2 天：推进主功能
- 1 天：补 UI / 交互 / 资源组织
- 1 天：调试、复盘、整理问题
- 1 天：修正结构、补文档、准备下一阶段

## 使用要求

1. 不要跳着做，看起来更“高级”的部分往往不是当前最重要的；
2. 每篇文档都要有实际产出，不能只停留在读完；
3. 如果某一阶段验收没过，不进入下一阶段；
4. 源码理解要围绕当前 Demo 中遇到的真实问题回看，而不是脱离项目盲读。

## 交付标准

你真正完成这套执行路径，不是因为文档都看过了，而是因为你最终具备了这些结果：

- 有一个能运行的 Demo；
- 有一套能解释自己系统边界的项目结构；
- 有一份可复盘的问题清单；
- 有一批下一次可以复用的模块候选。
