# 04 - UI 与交互流

## 目标

让玩家能够看懂、能顺畅操作、不会被界面打断理解。这个阶段的重点不是“把界面做得华丽”，而是让玩法信息和交互流清楚可靠。

## 前置

开始前应该已经具备：

- 战斗最小闭环已完成；
- 数据与战斗逻辑已经初步分层；
- 你已经知道哪些操作会频繁发生：抽牌、出牌、结束回合、查看意图、看伤害结果。

## UI 设计原则

### 1. 先清楚，再好看

优先保证：

- 当前回合是谁；
- 当前能量多少；
- 当前手牌有哪些；
- 敌人下一步想做什么；
- 当前打牌是否会生效。

只要这些信息表达不清楚，再漂亮的界面都无法支撑试玩。

### 2. 用界面承接系统边界

界面结构应该帮助你理解系统，而不是把系统搅乱。比如：

- 手牌区域负责卡牌展示与交互；
- 角色面板负责生命、格挡、状态展示；
- 战斗日志或提示区负责说明发生了什么；
- 结算界面负责奖励与跳转。

### 3. 用信号串联，而不是大量硬引用

UI 层非常容易因为互相直接调用变得难维护。能用信号表达“发生了一件事”，就不要大量让一个面板直接操控另一个面板内部状态。

## 执行步骤

### 第 1 步：稳定主界面流转

至少要有：

- 主菜单
- 战斗界面
- 战斗结果界面
- 可选奖励界面

最重要的是切换时机清楚，不要让一个脚本同时负责加载场景、播动画、发奖励、改全局状态。

### 第 2 步：把战斗信息完整展示出来

你至少要明确展示：

- 玩家生命 / 格挡 / 能量
- 手牌内容
- 敌人生命 / 意图 / 状态
- 回合阶段

如果这些信息不稳定，玩家很难判断系统是否正常，开发者自己调试也会变难。

### 第 3 步：处理交互合法性

要明确这些问题：

- 能量不够时卡牌是否禁用；
- 不可出牌时 UI 如何反馈；
- 正在结算时是否允许继续输入；
- 弹窗出现时是否要屏蔽下层输入。

### 第 4 步：处理反馈顺序

你要确保：

- 先计算逻辑结果；
- 再按顺序展示反馈；
- 展示结束后再进入下一状态。

这样才能避免“血量已经变了但动画还没播完”“玩家还能继续点下一张牌”的混乱。

### 第 5 步：补最小提示系统

不需要复杂日志系统，但至少应有：

- 关键动作提示；
- 回合开始/结束提示；
- 非法操作反馈；
- 敌人意图说明。

## 阶段产出

- 一个玩家能看懂的战斗界面；
- 一套稳定的主流程界面切换；
- 一套基本清楚的交互反馈；
- 一个不会频繁因为 UI 耦合而返工的界面结构。

## 验收

- 玩家能看懂当前回合和主要状态；
- 出牌时有明确反馈；
- 弹窗和界面层级不会互相打架；
- 战斗结算与视觉反馈顺序一致；
- 主要 UI 节点职责能被清楚解释。

## 常见坑

1. **逻辑直接写在 UI 组件里**：看起来方便，后期最难维护。
2. **输入控制不统一**：导致结算中还能继续操作。
3. **所有反馈一起跳**：玩家看不清到底发生了什么。
4. **界面层级没有约束**：弹窗、提示、按钮互相遮挡。
